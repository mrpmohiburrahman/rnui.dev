1The catalog is not in a database. 277 entries live in 18 hand-edited TypeScript files under data/ and get compiled into the bundle.
2Firestore stores exactly two numbers per item — view_count and vote_count. Nothing else. There is no products table anywhere in the live path.
3State is split three ways: Firestore is global and shared, localStorage is per-device and private, React state is per-render. There is no auth, so 'have I voted' can only ever be a device fact.
4All video and thumbnail bytes are served by ImageKit's CDN. data/*.ts stores relative paths; lib/imagekit.ts prefixes the endpoint and appends transform params at render time.
5A separate AI layer (codex:*) automates contribution — GitHub URL in, validated data/ entry and a PR out — plus embedding-based search over a JSON file.
6Supabase is wired up but dormant. Its client, server, and middleware helpers exist; every call site that used it is commented out.

Layer 01

Content Is Code

The single most important thing to internalise: adding an animation to this site means editing a TypeScript file and shipping a deploy, not writing a row.

⬡ Key Concepts

Concept

18 files, one array each

data/accordions.ts, data/buttons.ts, data/misc.ts … each exports a typed ItemType[]. misc.ts alone holds 148 of the 277 entries — it is the catch-all and by far the largest file at ~77 KB.

Concept

ItemType is the schema

id (ULID), caption, videoSrc, thumbnailSrc, author, source, optional twitterId/linkedInId/githubId, and category — a hardcoded 18-member string union, not a lookup table.

Concept

Aggregated twice

data/items.ts spreads all 18 arrays into localItems. lib/codex/items.ts spreads the exact same 18 into ALL_ITEMS. Two aggregators, two import lists to keep in sync when a category is added.

Concept

Categories declared three times

As the union on ItemType.category, as CATEGORY_VALUES in lib/codex/schema.ts, and as the redirect map in middleware.ts. Nothing enforces agreement between them.

▸ Playbook: Content Is Code
  1. Pick the right data/.ts file — or misc.ts if nothing fits.
  2. Generate a ULID for id (the codex ingest script uses the ulid package).
  3. Set videoSrc/thumbnailSrc to relative paths — no domain, imagekit.ts adds it.
  4. If you add a whole new category, update the union in items.ts, CATEGORY_VALUES in codex/schema.ts, the spread in data/items.ts, AND the spread in lib/codex/items.ts.

Layer 02

The Request Path

One request touches the local arrays, one Firestore round-trip, and then hands a fully-materialised list to the client. Nothing is paginated.

⬡ Key Concepts

Concept

layout.tsx runs sync

getUniqueCategories() and getUniqueAuthors() are plain array ops over localItems — no await, no fetch. The sidebar is free because the catalog is already in memory.

Concept

getProducts is the only read

A "use server" + server-only action wrapped in React cache(). It calls getItemsWithCounts(), then filters by search / category / author entirely in JS.

Concept

Whole-collection read

getItemsWithCounts() issues getDocs(collection(db, COLLECTION_NAME)) — no where, no limit. It pulls every counts doc and builds a lookup map. Fine at 277; it is a linear cost, not a constant one.

Concept

Client takes over at the boundary

DirectoryPageClient is the "use client" seam. It owns four hooks — bookmarks, votes, modal, sorting — and renders the card grid. The virtualized grid uses @tanstack/react-virtual for long category lists.

▸ Playbook: The Request Path
  1. middleware.ts only handles 18 legacy category URLs (/buttons → /products?category=Buttons). It runs on nothing else.
  2. app/page.tsx is the home grid; app/products/page.tsx is the filtered grid; both call the same getProducts().
  3. FEATURED_IDS on the homepage is an empty array, so the featured grid always renders empty.
  4. label and tag are still threaded through getProducts as parameters but every filter body using them is commented out.

Layer 03

The State Split

Three stores, three lifetimes, no auth to reconcile them. Understanding which fact lives where explains most of the site's behaviour — and its quirks.

⬡ Key Concepts

Concept

Firestore — global, shared

One doc per item id, holding view_count and vote_count. Writes use increment(1); a not-found FirebaseError triggers a setDoc that creates the doc. Collection name comes from NEXT_PUBLIC_FIRESTORE_COLLECTION, defaulting to rnui.

Concept

localStorage — per device

votedItems and bookmarkedItems are string-id arrays. This is the only record of who voted for what. Clear it and you can vote again; bookmarks never sync anywhere.

Concept

React state — per render

ResourceCard keeps local voteCount/viewCount and bumps them optimistically alongside the server action, so the number moves before Firestore confirms.

Concept

⚠ Views double-count on vote

handleVoteClick in resource-card.tsx awaits incrementViewCountLocal(), then calls toggleVote(id) — and toggleVote in use-votes.ts also calls incrementViewCount(id). One vote click writes two view increments to Firestore.

▸ Playbook: The State Split
  1. Vote click → incrementViewCount, then toggleVote (which fires incrementViewCount again), then increment or decrement vote_count.
  2. Card click / link click → incrementViewCount only.
  3. Un-voting calls decrementVoteCount and clamps the optimistic local number at 0 — Firestore itself is not clamped.
  4. Because identity is localStorage-only, vote_count is a popularity signal, not a unique-voter count.

Layer 04

Media Pipeline

Two pipelines that never meet at runtime: an offline one that produces and uploads assets, and a runtime one that only builds URLs.

⬡ Key Concepts

Concept

Offline: encode → thumbnail → upload

convert-to-h265.js and convert-to-avif.js compress, generateThumbnails.ts shells out to ffmpeg over public/demo writing into public/thumbnails, and upload-to-imagekit.js pushes the result to the CDN.

Concept

Runtime: string concatenation only

lib/imagekit.ts has no SDK calls in the request path — it strips a leading slash and prepends NEXT_PUBLIC_IMAGEKIT_URL_ENDPOINT. That is the entire runtime cost.

Concept

Transforms are query params

Thumbnails default to tr=w-221,h-393,q-70,f-auto. LQIP blur-up uses tr=w-20,q-10,bl-20 for a ~1–2 KB instant placeholder. Video URLs currently ship without transforms — the quality argument is accepted and ignored.

Concept

Playback is viewport-gated

InteractiveVideo uses useIntersectionObserver so only visible clips play. layout.tsx emits preconnect and dns-prefetch for ik.imagekit.io to hide the handshake.

▸ Playbook: Media Pipeline
  1. Set IMAGEKIT_PUBLIC_KEY / IMAGEKIT_PRIVATE_KEY / IMAGEKIT_URL_ENDPOINT before running the upload script.
  2. NEXT_PUBLIC_IMAGEKIT_URL_ENDPOINT is the client-visible one — imagekit.ts warns to console if it is missing and silently emits broken URLs.
  3. next.config.ts deliberately narrows webpack watchOptions.ignored to node_modules only, so public/demo stays watchable in dev.

Layer 05

The Codex AI Layer

A bolt-on automation loop around contribution. It writes source code into data/ and answers search queries — but it is optional; the site runs fine with no OpenAI key.

⬡ Key Concepts

Concept

codex:ingest — URL in, PR out

gh api fetches repo metadata and README → gpt-4o-mini emits structured output → Zod validates against ExtractedEntrySchema → ts-morph appends the entry into data/<file>.ts preserving formatting → branch submission/<slug>, commit, push, PR.

Concept

codex:index — embed the catalog

embedMany with text-embedding-3-small over every item, written to data/embeddings.json as { model, generatedAt, vectors[] }.

Concept

/api/search — cosine over JSON

Reads the index once into a module-level cache, embeds the query, scores every vector with a hand-rolled cosine loop, returns top 20. Explicitly a stand-in for Supabase pgvector — the script comment says swap when the catalog outgrows JSON.

Concept

codex:review-pr — rubric triage

gh pr diff → gpt-4o-mini scored against a fixed rubric (schema compliance, duplicate ids, sensible category, video asset present, description quality) → posted back with gh pr comment.

▸ Playbook: The Codex AI Layer
  1. Everything AI-shaped needs OPENAI_API_KEY; requireOpenAIKey() in lib/codex/env.ts hard-exits the process when it is absent.
  2. /api/search degrades rather than crashes: 503 + 'Run pnpm codex:index' if embeddings.json is missing, 503 if the key is unset.
  3. Models are pinned in one place — CODEX_MODEL = gpt-4o-mini, CODEX_EMBED_MODEL = text-embedding-3-small.
  4. Re-run pnpm codex:index after adding items or the new entries are invisible to semantic search.

Layer 06

Automation & Gates

Four GitHub workflows and a husky hook chain. One of them is deliberately the only un-bypassable layer.

⬡ Key Concepts

Concept

ci.yml — quality

Runs on push to main / codex-grant-prep and on PRs to main. pnpm + the lint / type-check / test scripts.

Concept

codex-triage.yml — AI review

Fires on PR opened / synchronize / reopened with pull-requests: write. Skips itself when OPENAI_API_KEY is unset so fork PRs don't produce red checks.

Concept

no-ai-attribution.yml — the hard gate

Its own comment states the intent: local hooks die to git commit --no-verify, this does not. Runs on every push to every branch and is meant to be a required status check on main.

Concept

metrics-update.yml — weekly cron

Mondays 09:00 UTC, contents: write, runs metrics-update.ts which shells to gh and rewrites metrics/weekly.json.

Concept

⚠ The pre-commit tax

.husky/pre-commit chains update:lastcommit and update:updateChangedItems, auto-staging both outputs. Every single commit therefore churns scripts/lastCommitDate.json by a few milliseconds.

Concept

⚠ changedItems silently stalls

updateChangedItems.js checks out origin/main to diff against remote. When local main is ahead, the checkout aborts on the dirty lastCommitDate.json. The script catches the error, logs it, and exits 0 — so the hook passes while data/changedItems.json stops updating.

▸ Playbook: Automation & Gates
  1. data/changedItems.json is currently 3 bytes — consistent with the stalled updater described above.
  2. If a commit hangs or dirties lastCommitDate.json unexpectedly, the pre-commit chain is the cause, not your change.
  3. Fixing the stall means having updateChangedItems.js read origin/main via `git show origin/main:` instead of checking the branch out.

Layer 07

Vestigial Wiring

A meaningful share of the repo is a previous architecture left in place. Knowing what is dead is as load-bearing as knowing what is live.

⬡ Key Concepts

Concept

Supabase is dormant

db/supabase/ ships client.ts, server.ts, middleware.ts and mockSupabase.ts. The only two files that reference it — get-product-by-id.ts and get-filters.ts — have their entire bodies commented out. getProductById currently returns undefined.

Concept

getProducts kept its old body

The original Supabase query — .from("products").select("*") with ilike search and contains on labels/tags — is preserved as a comment block above the in-memory implementation that replaced it.

Concept

getCachedFilters is a stub with a side effect

It returns { categories: [], labels: [], tags: [] } through unstable_cache (revalidate 9000). Worse, displayFilters() is invoked at module top level, so importing the file console-logs three empty arrays.

Concept

Two analytics stacks

Vercel <Analytics /> and a PostHog provider both mount in the root layout. A recent commit switched PostHog to send events directly rather than through an /ingest proxy.

Concept

Theme provider, one theme

next-themes is configured with enableSystem, but defaultTheme="system" is commented out and hardcoded to "light".

▸ Playbook: Vestigial Wiring
  1. Before wiring anything to Supabase, decide whether it is being revived or removed — right now it is neither.
  2. Deleting cached_actions.ts removes a top-level side effect for free; nothing consumes getCachedFilters.
  3. If pgvector search ever lands, get-filters.ts and the commented getProducts query are the intended shape to restore.

Action Items

Checklist

🧭 Onboarding — read in this order
  • data/items.ts — ItemType, the 18-way spread, getItemsWithCounts()
  • app/actions/get-products.ts — the single read path (ignore the commented Supabase block)
  • app/layout.tsx then app/page.tsx — where server ends and client begins
  • components/directory-page-client.tsx — the four hooks that own all client state
  • lib/imagekit.ts — why no media is served from your own origin
➕ Adding an animation
  • Drop the clip in public/demo//
  • pnpm generate-thumbnails (needs ffmpeg on PATH)
  • node scripts/upload-to-imagekit.js with the three IMAGEKIT_* vars set
  • Append the ItemType entry with a fresh ULID to data/.ts
  • pnpm codex:index to refresh embeddings.json, or the item won't be searchable
  • pnpm test — tests/data-integrity.test.ts is the guard for malformed entries
🐞 Known rough edges, in severity order
  • Voting writes incrementViewCount twice (resource-card.tsx handleVoteClick + use-votes.ts toggleVote)
  • updateChangedItems.js silently stops updating data/changedItems.json whenever local main is ahead of origin/main
  • cached_actions.ts invokes displayFilters() at module scope — a side effect on import, returning empty arrays
  • getProductById returns undefined; anything calling it gets nothing rather than an error
  • Category list is declared in three places with nothing enforcing agreement
  • getItemsWithCounts reads the entire Firestore collection per uncached request
🔑 Environment variables that matter
  • NEXT_PUBLIC_FIRESTORE_COLLECTION — defaults to "rnui"; how prod and dev counts stay separate
  • NEXT_PUBLIC_IMAGEKIT_URL_ENDPOINT — missing means every media URL is silently broken
  • IMAGEKIT_PUBLIC_KEY / IMAGEKIT_PRIVATE_KEY — upload script only
  • OPENAI_API_KEY — all codex:* scripts and /api/search; absent is handled, not fatal to the site
