# The domain is Recording and Contributor

`CONTEXT.md` called a catalogue record an **Entry** and the person who made it an `author`, and ADR-0004 renamed the code to match. The design this repo is now building calls neither of those things by those names anywhere it names them: `RN UI RECORDINGS` in the header, `CONTRIBUTORS · 24` above the rail, `Search 277 recordings` in the search field, `← All recordings` on the detail, `MORE FROM THIS CONTRIBUTOR` below it, and `This recording won't play in your browser` on a failed tile (`assets/new-ui/Catalogue.dc.html`, `Detail.dc.html`, `Tile.dc.html`). We are renaming the domain to **Recording** and **Contributor**, in code and in copy, because building ten routes of that copy on top of a type called `Entry` and a field called `author` produces exactly the failure ADR-0004 exists to prevent — a reader who learns the vocabulary from `CONTEXT.md` and then opens the code learns it twice.

The timing is not incidental. ADR-0004 rejected deferring its own rename into the work that rewrote those files, "to avoid a period in which half the codebase speaks each vocabulary". Renaming after the Studio Dark build would create that period across ten routes instead of three.

## Considered options

- **Rename the user-facing copy only, and add a display-vocabulary layer to `CONTEXT.md`.** Code keeps `Entry` and `author`; the UI says recording and contributor. No data churn and no migration. Rejected by the maintainer: it re-creates two vocabularies deliberately rather than accidentally, and every future reader has to hold both.
- **Rename after deploy A, alongside the redesign.** One less commit before the site ships. Rejected because two of the three public names stop being free on that deploy — see below — and because `posthog-expansion` dashboard `1937576` would then read a property rename as a hole in its funnel rather than an error.
- **Rename `?author=` freely, as `.scratch/studio-dark/spec.md` originally assumed.** Rejected on inspection: the parameter is already live. `main`'s `components/nav/catalogue-nav.tsx:77` writes `/products?author=…` on every contributor link, and `main`'s `app/products/page.tsx` reads it. The spec's claim that it was "new in ticket 11" confused the composition of filters, which is new, with the parameter, which is not.

## Consequences

- **Two public names were renamed for free, and one was not.** `/entry/[id]` and the `entry_id` property on all thirteen PostHog events are absent from `main` — `git ls-tree -r --name-only main` lists neither `app/entry/` nor `lib/analytics.ts` — so not one of the 277 addresses has ever been served and not one event has ever been ingested. They cost a `git mv` and a commit today; after deploy A they cost 277 redirects and a property migration against ingested data. `?author=` was already live and therefore keeps a `permanentRedirect` in `app/products/page.tsx` rather than being renamed away.
- **Four names were deliberately not renamed**, on the boundary ADR-0004 drew for itself: `/products` and `?category=`, which `middleware.ts` exists specifically to keep alive for 18 legacy Category URLs, and the Firestore field names `view_count` and `vote_count`, which are keys inside live documents. Changing any of them is a migration, not a rename.
- **Three stored browser keys were not renamed either.** `"bookmarkedItems"`, `"votedItems"` and `"viewedEntryIds"` keep their exact stored strings while their constants became `BOOKMARKS_KEY`, `VOTED_RECORDING_IDS_KEY` and `VIEWED_RECORDING_IDS_KEY`. The first two are Remembered sets, and renaming one discards every bookmark a visitor has already made. The third is a sessionStorage key, but ADR-0007 makes the once-per-Recording-per-session cap load-bearing: change the string and every tab open at deploy bills a second view for everything already watched.
- **One event name changed and twelve did not.** `entry_opened` became `recording_opened`, and its `source` property became `opened_from`. `posthog-expansion/issues/03-instrument-catalogue-events.md` raised that collision as a question an agent would not answer unilaterally — in this repo `source` is a Recording's outbound link to the contributor's code, and `repo_clicked` is the event about following it, so an `entry_opened.source` of `card` meant something else entirely. `demo_played`, `demo_watched`, `demo_load_failed`, `repo_clicked`, `filter_applied`, `filter_cleared`, `search_performed`, `sort_changed`, `bookmark_added`, `bookmark_removed`, `vote_cast` and `load_more_clicked` are byte-identical.
- **`git blame` on 277 data lines now points at this commit** rather than at the submission that added the Recording. ADR-0004 accepted the same cost for the same files, on the same reasoning: the data files are append-only lists where blame carries little.
- **The diff cannot be reviewed by reading**, for the same reason ADR-0004's could not. The review is `pnpm assets:paths` captured before and after: 554 lines, hashing to `6c98ad304e952cdeea03789f772574ca83d87bb3bdf32cedb668edac10a0694d` on both sides. A single changed character would mean the rename reached data rather than names, which is the only failure mode the diff cannot show.
- **Two JavaScript builtins had to be excluded by hand** after a word-boundary pass caught them: `Map.prototype.entries()` in `tests/data-integrity.test.ts` and `PerformanceObserverEntryList.getEntries()` in `tests/e2e/theme.spec.ts`. `Object.fromEntries` in `data/categories.ts` was safe only because no word boundary falls inside it. A future rename of a word this common should expect the same.
